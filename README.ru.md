# RunPilot

**Языки:** [English](README.md) | Русский

[![Go](https://img.shields.io/badge/Go-1.26-00ADD8)](https://go.dev)
[![License: MIT](https://img.shields.io/badge/License-MIT-70b000.svg)](LICENSE)

**RunPilot** — self-hosted контрольная панель для AI-кодеров. Планирует,
проксирует, мониторит и визуализирует сессии кодинг-агентов (Qwen Code в tmux)
на одной или нескольких машинах, за одним статическим бинарником на Go.

- Один статический бинарник (`CGO_ENABLED=0`), три роли: координатор, узел, клиент
- Слотовое планирование с аренами, очередью и миграцией на лету
- Прозрачный LLM-шлюз — кодеру достаточно указать `OPENAI_BASE_URL`
- Живой web UI: сессии, очередь, серверы, узлы, журнал, мониторинг, инлайн-терминал
- Режимы оператора: `NORMAL` / `PAUSED` / `EMERGENCY` / `SAFE_MODE`
- Встроенный мониторинг (health, метрики vLLM, GPU) и карантин отказов
- Уведомления в Telegram, retention и бэкапы
- Многомашинный режим поверх частной сети-оверлея (например, Tailscale)

## Что это

RunPilot координирует кодинг-агентов, живущих в tmux-панелях. **Координатор**
принимает все решения (планирование, аренды, мониторинг); **узлы** работают на
машинах, где живут сессии, и управляют только локальными tmux-панелями; единый
**шлюз** стоит перед LLM-серверами, чтобы кодеры обращались к одному URL. Отдельной
сборки фронтенда нет — web UI встроен в бинарник.

| Роль | Команда | Где работает |
|---|---|---|
| Координатор | `runpilot serve` | на хаб-машине |
| Узел | `runpilot node` | на каждой рабочей машине |
| Клиент | `runpilot` | с любой машины, достигающей координатор |

```
                 ┌────────────────────────── хаб ──────────────────────────┐
                 │                                                          │
 кодер ─────────►│  шлюз :8787  ──►  LLM-сервер A / B (vLLM)               │
 (в tmux-панели) │      │                                                   │
                 │      ▼                                                   │
                 │  координатор :8788  ──  планировщик · монитор · store     │
                 │      ▲  WebSocket                                         │
                 └──────┼──────────────────────────────────────────────────┘
                        │
                 ┌──────┴──────┐
                 │   узел      │   управляет tmux-панелями своей машины
                 └─────────────┘
```

- Кодеры общаются **только со шлюзом** (`OPENAI_BASE_URL=http://<coord>:8787/s/<sid>/v1`).
- Узлы общаются **только с tmux** своей машины (`tmux`, `ps`, `nvidia-smi`, `rocm-smi`).
- **Планировщик** — единственная компонента, решающая, когда сессия получает слот.

## Возможности

- **Жизненный цикл сессии** — старт, resume, run, attach, peek, закрытие; очередь
  с приоритетом, pin/hold; автоматический requeue при сбое.
- **Шлюз** — прозрачный reverse-прокси LLM-трафика с маршрутизацией по сессии,
  лимитом тела, удержанием слота и одноразовой миграцией при отказе апстрима
  до первого байта.
- **Планирование** — аренды слотов (не сырая GPU-загрузка), aging, affinity,
  cooldown, детекция внешних слотов, recovery-окно.
- **Мониторинг** — периодические health-проверки, `/metrics` vLLM и GPU,
  окна отказов с карантином упавшего сервера, детекция флэппинга.
- **Режимы оператора** — `NORMAL`, `PAUSED`, `EMERGENCY` (отмена всей идущей
  генерации), `SAFE_MODE` (новых аренд нет, идущие завершаются).
- **Web UI** — список и карточки сессий, очередь, серверы, узлы, журнал,
  мониторинг, уведомления, настройки; живой экран панели и инлайн-терминал;
  приём (adopt) существующих tmux-панелей; светлая/тёмная тема; вход по токену.
- **Уведомления** — Telegram-алерты по отказам, OOM, аварийному режиму, bind,
  БД и внешним процессам (коалесценция, rate-limit).
- **Данные** — SQLite (WAL), автоматический retention, ежедневный бэкап с
  rollback/restore.
- **Adopt** — принять существующую tmux-панель (где уже работает агент) под
  управление.

## Требования

- Go `1.26` для сборки из исходников.
- `tmux` на каждом узле (хостит сессии агентов).
- Частная сеть между хабом и узлами (референсный вариант — Tailscale).
  Для одной машины достаточно loopback.

## Аппаратные требования

Сам RunPilot лёгкий: координатору и узлам **не нужен** GPU. GPU-зависимая
часть — модельные серверы, на которые он указывает. Каждый элемент `servers`
целится в модельный сервер (обычно **vLLM**), работающий на GPU, подогнанном
под модель: например, модели класса 27B нужен GPU (или пул GPU) с VRAM,
достаточным для весов и памяти активаций. RunPilot читает health, `/metrics` и
GPU-нагрузку каждого сервера, но сам инференс не выполняет.

## Установка

Собираем единый бинарник:

```sh
go build -o runpilot ./cmd/runpilot
```

Устанавливаем службы (systemd на Linux; launchd-заглушка на macOS):

```sh
./runpilot service install serve   # координатор на хабе
./runpilot service install node    # узел на каждой рабочей машине
```

Каждая команда генерирует юнит, кладёт его и включает + запускает. Координатор
читает конфиг из `~/.config/runpilot/config.yaml` и секреты из
`~/.config/runpilot/env`. Узел читает свой `config.yaml` и `secrets.env`
(там токен узла).

> Бинарник полностью статический (`CGO_ENABLED=0`). Одинаковый артефакт
> можно разложить на все машины.

## Быстрый старт

1. Создайте конфиг координатора `~/.config/runpilot/config.yaml`
   (см. [Конфигурация](#конфигурация)).
2. Положите операторский токен в `~/.config/runpilot/env`:
   `RUNPILOT_TOKEN=...`.
3. `./runpilot serve` (или через установленную службу).
4. На каждом рабочем узле: `./runpilot node --config ~/.config/runpilot/config.yaml`.
5. Откройте web UI на координаторе (порт по умолчанию `8790`) и войдите по токену.
6. Запустите сессию — из web UI или:
   ```sh
   ./runpilot run --agent qwen --name mytask --dir ~/proj
   ```

Кодер внутри сессии настроен на шлюз, поэтому его LLM-запросы планируются,
учитываются и мониторятся RunPilot.

## Конфигурация

Строгий YAML (неизвестные ключи отклоняются). Полный референс и пример — в
[`testdata/config.example.yaml`](testdata/config.example.yaml); значения по
умолчанию — в [`internal/config/defaults.go`](internal/config/defaults.go).

Минимальный конфиг координатора:

```yaml
coordinator:
  bind: 127.0.0.1
  allow_cidrs: ["127.0.0.0/8", "100.64.0.0/10"]
  gateway_port: 8787
  api_port: 8788
  token_env: RUNPILOT_TOKEN
  db_path: ~/.local/share/runpilot/runpilot.db

servers:
  - name: srv1
    priority: 100
    slots: 1
    accept: [resume, high, normal, low]
    health_url: http://192.0.2.21:8004/health
    metrics_url: http://192.0.2.21:8004/metrics
    upstreams:
      openai:
        url: http://192.0.2.21:8004
        model: qwen3.6-27b
        key_env: RUNPILOT_KEY_VLLM

profiles:
  qwen: {model_alias: qwen3.6-27b}
```

### Переменные окружения

| Переменная | Назначение | Пример (не секрет) | Обязательно |
|---|---|---|---|
| `RUNPILOT_TOKEN` | Операторский токен (API + вход в web UI) | любая длинная случайная строка | да |
| `RUNPILOT_KEY_VLLM` | API-ключ, передаваемый LLM-серверу (имя задаётся на сервер через `key_env`) | ваш ключ провайдера | на сервер |
| `RUNPILOT_TG_TOKEN` | Токен Telegram-бота для алертов | ваш токен бота | нет |

Токен узла хранится в `secrets.env` узла (подключается установленным unit
`node` через `EnvironmentFile`). Значения читаются только из окружения и никогда
не хранятся в репозитории.

Все пороги, таймауты и лимиты читаются из конфигурации — в «горячем» коде нет
захардкоженных чисел.

## Командная строка

`runpilot` — клиент. Основные команды:

| Группа | Команды |
|---|---|
| Роли | `serve`, `node`, `doctor`, `selftest`, `version` |
| Сессии | `run`, `exec`, `ls`, `q`, `peek <t>`, `attach <t>`, `why <t>` |
| Очередь | `queue enqueue/dequeue/requeue/prio/pin/prefer/unpin/hold/unhold/set/cancel` |
| Серверы | `servers`, `server drain/undrain <s>`, `pause`, `resume` |
| Операции | `events`, `stats`, `backup restore/rollback`, `service install`, `upgrade`, `tmux-setup` |

Флаги — `runpilot <cmd> --help`. Коды выхода: `0` успех, `1` runtime-ошибка или
любой FAIL в `doctor`, `2` нарушение схемы/семантики конфигурации.

## Web UI

Секции: **Сессии**, **Очередь**, **Серверы**, **Узлы**, **Журнал**,
**Мониторинг**, **Уведомления**, **Настройки**. В карточке сессии — живой
экран панели, статус, активная аренда и **инлайн-терминал** для прямого ввода.
UI раздаёт координатор и защищён операторским токеном; рассчитан на доступ из
частной сети (например, через `tailscale serve`).

## Архитектура

RunPilot — один Go-модуль со строгим набором пакетов:

- `internal/config` — строгая схема, единственное место defaults, валидация.
- `internal/model` — сущности и автоматы состояний как чистые функции.
- `internal/store` — SQLite (WAL), миграции, retention.
- `internal/clock` — реальные/виртуальные часы (всё время — через них).
- `internal/gateway` — прокси, удержание слота, миграция.
- `internal/scheduler` — тик, ранги, допустимость, выбор сервера.
- `internal/monitor` — health, метрики vLLM, GPU, карантин отказов.
- `internal/api` — REST + SSE + WebSocket узлов.
- `internal/node`, `internal/tmux` — узловой демон и tmux-вызовы.
- `internal/detect` — классификация панелей и извлечение ввода.

Ключевые инварианты: не более N идущих ходов на сервер (N = его слоты); каждый
переход состояния сначала пишется в SQLite, потом — побочный эффект; значения
токенов и тела запросов никогда не логируются. Детали — в
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) и
[`docs/api.md`](docs/api.md).

## Структура проекта

```text
runpilot/
├── cmd/runpilot          # единый бинарник: роли координатор / узел / клиент
├── cmd/runpilot-stand    # офлайн-стенд для тестов (фикстуры, скриншоты)
├── internal/             # config, model, store, clock, gateway, scheduler, monitor, api, ...
├── web/                  # встроенный web UI (ESM-модули, без сборки)

├── testdata/             # фикстуры + config.example.yaml
├── tools/                # линтеры и генераторы проекта
├── docs/                 # ARCHITECTURE.md, api.md
├── Makefile
└── go.mod
```

## Разработка

```sh
go build ./...        # сборка
go vet ./...          # vet
make lint             # линтеры проекта (литералы / web / хосты)
go test -race ./...   # полный набор тестов
```

Все четыре проверки должны проходить. Линтеры обеспечивают гигиену кода,
включая запрет реальных имён машин и частных CGNAT-адресов.

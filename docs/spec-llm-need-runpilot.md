# Потребность MoxHome в LLM-эндпоинте (для оркестратора RunPilot)

> Документ для передачи оркестратору RunPilot: описание потребности MoxHome в
> LLM и способа взаимодействия. Оркестратор организует порт; MoxHome настраивает
> его как свой LLM-эндпоинт. Дата: 2026-10-22.

## 1. Потребитель
- **Проект:** MoxHome (переводчик EPUB/FB2), хост `3p14-aaa` (Tailscale `100.124.155.106`).
- **Процесс-клиент:** воркер MoxHome (`python -m app.workers.run`), резидентный.
- **Сейчас** LLM — локальный vLLM `127.0.0.1:8004` (модель `qwen3.8-27b`, FP8).
  Он не всегда свободен → нужен выделенный эндпоинт через RunPilot.

## 2. Что нужно
OpenAI-совместимый HTTP-эндпоинт (chat completions). MoxHome сам дописывает к
`base_url` путь `/chat/completions`. То есть оркестратор даёт `base_url` вида
`http://<host>:<port>/v1` — MoxHome шлёт `POST {base_url}/chat/completions`.

- **Активный протокол:** только `POST /v1/chat/completions` (пайплайн `single`,
  профили `translation`, `fill`, `analysis`).
- **Не требуется:** `POST /v1/completions` (профиль `mt`) — в текущем пайплайне
  не используется. Если оркестратору проще дать только chat — это достаточно.

## 3. Способ взаимодействия (контракт)
- **Метод:** `POST`, JSON, **без стриминга** (`"stream": false`).
- **Авторизация:** заголовок `Authorization: Bearer <API_KEY>`. Ключ — любой
  секрет, договоримся с оркестратором; MoxHome кладёт его в свой `.env`
  (`LLM_API_KEY`).
- **Поля запроса (MoxHome шлёт):** `model`, `messages`, `temperature`,
  `max_tokens`, `stream:false`, и `extra_body` (см. §4).
- **Ответ (MoxHome читает):**
  - `choices[0].message.content` — текст;
  - `choices[0].finish_reason`;
  - `usage.prompt_tokens`, `usage.completion_tokens` — для учёта токенов/стоимости;
  - **`model`** — имя модели в ответе.

## 4. Критичные требования к эндпоинту
1. **Имя модели.** Активные chat-профили **не** останавливают задание при
   несовпадении `model` в ответе (жёсткая сверка `model_mismatch` есть только у
   профиля `mt`/completions, в текущем пайплайне не используется). Но
   оркестратор не должен молча подменять модель — характеристики вывода
   различаются; если модель другая — сообщить, MoxHome перенастроит `model`
   в конфиге.
2. **Пропуск `extra_body` (vLLM-расширение).** Для thinking-моделей MoxHome шлёт
   `chat_template_kwargs: {enable_thinking: false}`, иначе reasoning-поток
   попадает в контент ответа. Эндпоинт должен либо быть vLLM (примет
   `chat_template_kwargs`), либо отдавать **не-thinking** модель (тогда поле
   можно убрать из конфига MoxHome).
3. **Поддержка:** `temperature`, `max_tokens`, `stop`, `top_k`.

## 5. Паттерн запросов (нагрузка)
- **Конкурентность: 1** (один запрос за раз).
- **Размер запроса:** вход до ~2600 токенов группы + системный промпт/контекст
  ≈ **3–4K входных токенов**; выход до ~2–3K токенов. Контекст-окно **8–16K
  достаточно**, 32K+ желательно.
- **Таймауты:** 300 c (translation/fill), 120 c (analysis), прогрев 900 c.
- **Повторы:** 3, только на транспортные отказы (таймаут / 5xx / обрыв).
- **Длительность:** одна книга = сотни запросов, задание длится до часов.
  Клиент устойчив к временной недоступности (повторы + ожидание).

## 6. Подключение
- Клиент на `3p14-aaa`; порт может быть на любом хосте, **достижимом по
  Tailscale** с `3p14-aaa` (или на самом `3p14-aaa`).
- Механизм смены эндпоинта у MoxHome — уже есть: достаточно задать в
  `config/config.yaml` для профилей `base_url` + `model`, и `LLM_API_KEY` в
  `.env`. Других изменений кода не требуется.

## 7. Что просить у оркестратора (резюме для тикета)
1. Выделить OpenAI-совместимый порт (chat completions, без стриминга) с
   Bearer-auth, доступный с `3p14-aaa` по Tailscale.
2. Уточнить: имя модели (для `model` в конфиге и для сверки в ответе),
   контекст-окно, thinking/не-thinking (нужен ли `chat_template_kwargs`).
3. Выдать API-ключ.

После получения: MoxHome прописывает `base_url`/`model`/ключ и проверяет кнопкой
«Проверить» на экране «LLM и модели» (probe-запрос `max_tokens: 8`).

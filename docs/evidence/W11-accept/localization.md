## Вывод

1. **Шлюз работает корректно.** В 1b соединение runpilot→vLLM (fd=16) закрывается
   за ≤100 мс после kill клиента. ReverseProxy/r.Context() cancel → upstream разорван.
   Локализация «internal/gateway/proxy.go» из прошлой приёмки **неверна** — шлюз
   не виноват.

2. **Звено, где обрыв не доходит до отмены: сам vLLM.** Даже ПРЯМОЙ запрос (1a,
   без шлюза) с kill -9 curl даёт stop+1, а не abort+1: vLLM догенерировывает
   ответ убитого клиента до конца. `vllm:request_success_total{finished_reason="abort"}`
   остаётся 0, строк об отмене/разрыве в журнале контейнера нет.

   То есть API-сервер vLLM (v0.30.0, кастомный билд) **не отменяет запрос при
   обрыве TCP-соединения клиента**. Разрыв соединения (FIN от килled-процесса)
   до механизма отмены движка не доходит.

## Звено вне репозитория: vLLM (Docker-контейнер)

- **Звено:** API-сервер vLLM в контейнере `vllm-qwen38-27b-dual-ultramax`.
- **Конфиг (docker inspect):**
  - image: `vllm/vllm-openai:v0.30.0` (кастомный билд, build commit `ced6857a`,
    buildkite release-v2/7022; патчи FA2, dflash-spec, GDN-async-order).
  - ключевые аргументы: `--max-num-seqs 2`, `--enable-prefix-caching`,
    `--enable-chunked-prefill`, `--max-model-len 262144`, `--tensor-parallel-size 2`,
    `--port 8000` (host 8004).
  - порт: `0.0.0.0:8004->8000/tcp`.
- **Предлагаемое изменение:** API-сервер vLLM обязан отменять запрос при обрыве
  клиента (abort → `finished_reason="abort"`). В стандартном vLLM это делается
  отменой async-генератора стрима при disconnect клиента; в данном кастомном
  билде отмена не срабатывает. Варианты:
  1. Исправить кастомный билд vLLM: при обрыве соединения клиента вызвать
     `abort_request` для соответствующего request-id (дополнить обработчик
     streaming на disconnect → cancel).
  2. Проверить, нет ли в билде отключённого/сломанного обработчика client
     disconnect (regression патчей FA2/spec).
  3. Альтернатива (если билд не правится): прокси перед vLLM, который при
     обрыве клиента закрывает upstream-соединение И посылает vLLM сигнал
     отмены — но стандартного OpenAI-эндпоинта отмены нет, так что это не
     решит проблему без изменения самого vLLM.

**Статус: остановка до решения оператора.** Рецепт vLLM не менять (п.2 ТЗ).
Критерий приёмки (п.3: 10× kill -9 exec, abort +1 ≤ 3 с) не выполним, пока vLLM
не отменяет запрос при обрыве клиента.
